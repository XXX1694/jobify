Backend Deep-Dive

Jobify API

IT job platform с матчингом навыков, Kanban-трекером заявок и фоновой агрегацией вакансий из Remotive

⚙️ Go 1.23 🐘 PostgreSQL 16 ⚡ Redis 7 🐳 Docker multi-stage 🔐 JWT RS256-like
1 Что такое Jobify

Jobify — REST API бэкенд для IT job-платформы. Разработчик создаёт профиль со скиллами, просматривает вакансии, получает match score (насколько его навыки совпадают с требованиями), добавляет вакансии в Kanban-трекер (saved → applied → interview → offer → rejected) и сохраняет их в шортлист. Администратор управляет вакансиями через CRUD. Фоновый воркер каждые 6 часов тянет новые вакансии с Remotive API и дедублицирует их.

2 Архитектура и слои

Проект построен на Clean Architecture с чёткими слоями и правилом: каждый слой знает только о нижнем.

cmd/api/main.go
Точка входа. Инициализация конфига, подключение к БД и Redis, ручная DI (без wire/fx), запуск воркера, настройка HTTP-сервера, graceful shutdown через signal.NotifyContext.
internal/handler/
HTTP-слой. Парсинг запроса, валидация, вызов сервиса, формирование ответа через pkg/response. Никакой бизнес-логики. Роутер — Chi v5. Порядок middleware: RequestID → Logger → CORS → BodyLimit → RateLimit → JWTAuth → RequireRole.
internal/service/
Бизнес-логика. Принимает интерфейсы репозиториев — не конкретные типы. Рассчитывает match score, уведомляет о конфликтах, orchestrates вызовы нескольких репо. Чист от HTTP-контекста.
internal/repository/
Интерфейсы в interfaces.go. Реализации в postgres/ (pgx, raw SQL) и redis/ (кэш, rate limit store, token store). Слой service зависит только от интерфейсов.
internal/domain/
Модели (User, Job, Application, DeveloperProfile, SavedJob) и доменные ошибки (ErrNotFound, ErrConflict, ErrUnauthorized, ErrForbidden). Дно — ни от чего из internal не зависит.
internal/middleware/
Каждый middleware в отдельном файле: auth.go, logger.go, rate_limit.go, body_limit.go. Навешиваются в router.go.
internal/worker/
Background goroutine — JobAggregator. Тикер каждые 6 часов, дедупликация по source_id, graceful stop через context.
pkg/
Переиспользуемые утилиты без привязки к домену: jwt, hasher, response, validator. Могут импортироваться из любого слоя.

4 Middleware

Порядок применения в router.go: Recoverer → RequestID → BodyLimit → CORS → RateLimit (глобально), затем JWTAuth → RequireRole для защищённых групп.

Recoverer (chi)
Перехватывает panic, возвращает 500. Встроенный в Chi — идёт первым, защищает весь стек.
RequestID (chi)
Генерирует уникальный X-Request-Id для каждого запроса. Встроенный в Chi.
BodyLimit
Ограничивает тело запроса до 1 МБ через http.MaxBytesReader. Защита от payload flood.
CORS (go-chi/cors)
AllowedOrigins: *. Методы: GET, POST, PUT, DELETE, OPTIONS. Хедеры: Accept, Authorization, Content-Type.
RateLimit
Redis INCR + EXPIRE по ключу rl:<ip>:<minute>. Лимит задаётся через RATE_LIMIT_PER_MIN (по умолчанию 60). При ошибке Redis — fail open (не блокирует). 429 + Retry-After: 60. Поддерживает X-Forwarded-For.
Logger
Кастомный. Оборачивает ResponseWriter, перехватывает статус-код. Логирует method, path, status, duration, remote через slog в JSON.
JWTAuth
Парсит Authorization: Bearer <token>. Валидирует JWT через pkg/jwt.Manager. Кладёт user_id и role в context. 401 при невалидном токене.
RequireRole
Проверяет role из context. Сейчас используется для группы admin. 403 Forbidden при несоответствии. Применяется после JWTAuth.

6 Docker — образы и конфигурация

Multi-stage Dockerfile

Stage 1: builder — golang:1.22-alpine
Скачивает зависимости (go mod download), компилирует бинарник с флагами CGO_ENABLED=0 GOOS=linux GOARCH=amd64 -ldflags="-s -w". Результат: /bin/api (~12 MB stripped).
Stage 2: runtime — alpine:3.20
Только ca-certificates + tzdata. Создаётся непривилегированный пользователь appuser. Копируется только бинарник. Нет исходников, нет компилятора, нет shell-утилит. Образ ~15 MB.

docker-compose.yml — три сервиса

7 Аутентификация — как работает
1. POST /auth/login → сервис проверяет bcrypt(password, hash)
2. Генерируется access_token (JWT, 72 ч) + refresh_token (UUID, 7 дней)
3. refresh_token сохраняется в Redis: key=token, value=user_id, TTL=7d
4. Клиент хранит оба токена (localStorage в браузере)

При запросе к защищённому endpoint:
   JWTAuth middleware → парсит Bearer 
   → извлекает user_id + role → кладёт в context

Когда access_token истёк (401):
   Axios interceptor → POST /auth/refresh { refresh_token }
   → Redis lookup → новая пара токенов → повтор запроса
   Если refresh тоже истёк → 401 → AUTH_EXPIRED_EVENT → logout

POST /auth/logout:
   Redis DEL(refresh_token) → token инвалидирован
8 Кэширование вакансий в Redis

Список вакансий (GET /jobs) кэшируется в Redis. Ключ строится из параметров фильтра: jobs:page=1:limit=20:skills=[go]:remote=true. В кэше хранится JSON-структура {jobs: [...], total: N} — оба поля вместе, чтобы пагинация возвращала правильный total. TTL — 30 секунд по умолчанию.

При создании, обновлении или удалении вакансии (admin) вызывается cache.Invalidate(ctx) — Redis SCAN по паттерну jobs:* с пакетным DEL. Ошибка инвалидации логируется, но не прерывает операцию записи (fail soft).

9 Background Worker — Job Aggregator

worker.JobAggregator запускается в отдельной goroutine в main.go. Использует time.Ticker на 6 часов. При старте сразу делает первый прогон. Fetches вакансии из Remotive API (IT remote jobs), маппит в domain.Job, проверяет дубликаты по source_id (ExistsBySourceID), сохраняет только новые. Остановка через ctx.Done() — корректный graceful shutdown.

10 Match Score — алгоритм

Функция CalculateMatch(userSkills, jobSkills []string) в service/job_service.go возвращает три значения: 

percent  = len(matched) / len(jobSkills) * 100
matched  = навыки, которые есть у юзера И требует вакансия
missing  = навыки вакансии, которых нет у юзера

Сравнение case-insensitive (strings.EqualFold).
Если jobSkills пуст — percent = 0.

Результат возвращается в GET /jobs/{id} как поля match_percent, matched_skills, missing_skills.

11 20 вопросов на интервью
1Какую архитектуру использует проект и почему?
Clean Architecture с слоями handler → service → repository → domain. Каждый слой знает только о нижнем, зависимости инвертированы через интерфейсы в repository/interfaces.go. Это позволяет тестировать сервисный слой с мок-репозиториями без поднятия БД, менять реализацию (например, заменить pgx на что-то другое) без изменения бизнес-логики.
2Как устроен JWT в проекте? Почему два токена?
access_token (JWT, 72 ч) — используется в каждом запросе, хранится только у клиента. Короткий TTL снижает риск при компрометации. refresh_token (случайный UUID, 7 дней) — хранится в Redis (key=token, value=user_id). Позволяет получить новый access_token без повторного логина. При logout Redis DELETE инвалидирует его немедленно, в отличие от JWT который нельзя отозвать.
3Почему GIN-индекс для массива skills, а не обычный?
B-tree индекс не умеет индексировать содержимое массивов. GIN (Generalized Inverted Index) создаёт отдельные записи для каждого элемента массива и поддерживает операторы @> (contains), && (overlap). Запрос skills @> '{go,redis}' использует GIN эффективно — без него был бы seq scan по всей таблице jobs.
4Что такое rate limiter и как он реализован?
Middleware в internal/middleware/rate_limit.go. Алгоритм — fixed window: ключ Redis = rl:<ip>:<minute> (минута из Unix timestamp / 60). INCR атомарно увеличивает счётчик, EXPIRE ставится только при count==1 (один вызов на окно). При превышении лимита — 429 + Retry-After: 60. Если Redis недоступен — fail open (не блокирует запросы), потому что недоступность кэша не должна ронять API.
5Как работает кэширование вакансий? Как инвалидация?
GET /jobs строит ключ из всех параметров фильтра и ищет в Redis. При cache miss — запрос к Postgres, результат кладётся в Redis как {jobs, total} (чтобы пагинация знала реальный total, не только размер текущей страницы). TTL — 30 секунд. При создании/обновлении/удалении вакансии (admin) — Invalidate() делает Redis SCAN jobs:* и пакетный DEL. Ошибка инвалидации логируется и игнорируется — write-операция не должна фейлиться из-за кэша.
6Как реализован graceful shutdown?
В main.go: signal.NotifyContext ловит SIGINT/SIGTERM. По сигналу вызывается cancel() — отменяется корневой контекст, воркер получает ctx.Done() и останавливает тикер. Параллельно srv.Shutdown(shutdownCtx) ждёт завершения активных соединений (до 10 секунд). Только после этого процесс завершается.
7Почему pgx/v5 без ORM?
pgx — нативный PostgreSQL драйвер для Go, в разы быстрее database/sql (бинарный протокол, pipelining). Raw SQL даёт полный контроль над запросами, нет N+1 проблем, нет "магии" ORM которая генерирует неоптимальные JOIN-ы. Для небольшой команды SQL читается явно — понятно что именно идёт в БД. pgxpool — встроенный connection pool с health checks.
8Как устроен Docker — что такое multi-stage build и зачем?
Stage 1 (builder, golang:1.22-alpine): компилирует Go-бинарник. Stage 2 (runtime, alpine:3.20): копирует только готовый бинарник. Итоговый образ ~15 MB вместо ~300+ MB если бы был один stage с Go SDK. В образе нет компилятора, нет исходников, нет лишних утилит — меньше attack surface. Пользователь appuser непривилегированный (не root).
9Как DI (Dependency Injection) организована в проекте?
Ручная DI в cmd/api/main.go без wire/fx. Сначала инициализируются инфраструктурные зависимости (db, redis), затем репозитории, потом сервисы (принимают интерфейсы репозиториев), затем хендлеры (принимают сервисы), затем роутер. Всё явно — нет рефлексии, нет магии, легко читается и дебажится.
10Как защищены admin-только маршруты?
В router.go admin-эндпоинты (POST/PUT/DELETE /jobs) обёрнуты в дополнительную группу Chi с middleware RequireRole("admin"). Этот middleware читает role из контекста (поставленного JWTAuth) и возвращает 403 если роль не совпадает. Порядок: JWTAuth (проверяет токен) → RequireRole (проверяет роль).
11Что такое domain errors и зачем они нужны?
В internal/domain/errors.go объявлены сентинел-ошибки: ErrNotFound, ErrConflict, ErrUnauthorized, ErrForbidden, ErrInvalidInput. Репозитории оборачивают pgx-ошибки в эти доменные, сервисы пробрасывают их вверх, хендлеры маппят на HTTP-коды через errors.Is. Это развязывает HTTP-слой от деталей БД.
12Как реализована пагинация в /jobs?
Query-параметры page и limit передаются в repository.JobFilter. В SQL: LIMIT $n OFFSET $m где offset = (page-1)*limit. Параллельно в том же запросе или отдельным COUNT(*) считается total. Ответ обёрнут в response.WithMeta — добавляет поля total, page, limit, pages.
13Как работает Job Aggregator? Как избегаются дубликаты?
Background goroutine с time.Ticker на 6 часов. При каждом тике: запрос к Remotive API, маппинг ответа в domain.Job (source="remotive", source_id=строка из Remotive). Перед вставкой — ExistsBySourceID(ctx, sourceID): SELECT COUNT WHERE source_id=$1. Если существует — пропуск. Новые вакансии вставляются по одному. Ошибки логируются, но не останавливают воркер.
14Как происходит upsert профиля?
PUT /me всегда вызывает profileRepo.Update(). Update делает SQL UPDATE WHERE user_id=$n. Если затронуто 0 строк — pgx возвращает ErrNoRows, репо конвертирует его в domain.ErrNotFound. Сервис ловит ErrNotFound через errors.Is и вызывает profileRepo.Create() с новым uuid.New(). Это решает проблему admin-пользователей у которых нет записи в developer_profiles.
15Как тестируется проект?
  • Сервисный слой — unit-тесты с ручными мок-репозиториями (структуры реализующие интерфейс)
  • Middleware — unit-тесты через httptest.NewRecorder + httptest.NewRequest
  • pkg/jwt, pkg/hasher, pkg/validator — unit-тесты на утилиты
  • Все тесты table-driven: tests := []struct{name; ...}{} + t.Run(tt.name, ...)
  • Нет интеграционных тестов с реальной БД (пока)
16Какой формат HTTP-ответов?
Все ответы через pkg/response. Конверт: {"success": true/false, "data": ..., "error": "...", "meta": {...}}. response.JSON — успех с data. response.Error — ошибка с error-строкой. response.WithMeta — список с пагинационным meta. Content-Type всегда application/json.
17Что такое views_count и как он обновляется?
Поле views_count BIGINT в таблице jobs. При каждом GET /jobs/{id} вызывается jobRepo.IncrementViews(ctx, jobID) — атомарный UPDATE jobs SET views_count = views_count + 1 WHERE id=$1. Индекс idx_jobs_views_count DESC поддерживает сортировку по популярности. Инкремент происходит независимо от авторизации (но endpoint защищён JWT).
18Почему порты в docker-compose нестандартные (5433, 6380)?
Если на хост-машине уже запущен локальный Postgres на 5432 или Redis на 6379, docker-compose не запустится из-за конфликта портов. Нестандартные порты хоста (5433→5432, 6380→6379) позволяют запускать оба окружения одновременно. Внутри Docker-сети контейнеры общаются по стандартным портам (api подключается к postgres:5432 и redis:6379).
19Как настраивается приложение? Какие env-переменные обязательны?
Конфиг читается один раз в main.go через config.Load() (internal/config/config.go). Поддерживается .env через godotenv.
  • DATABASE_URL — обязателен. Postgres DSN
  • JWT_SECRET — обязателен. Секрет для подписи JWT
  • HTTP_PORT — дефолт 8080
  • REDIS_ADDR — дефолт localhost:6379
  • REMOTIVE_API_URL — дефолт remotive.com/api/remote-jobs
  • RATE_LIMIT_PER_MIN — дефолт 60
20Как Kanban-трекер заявок работает на уровне БД?
Таблица applications с полем status VARCHAR(50). Значения: saved, applied, interview, offer, rejected. Constraint UNIQUE(user_id, job_id) — пользователь не может дважды откликнуться на одну вакансию. Смена статуса — PUT /applications/{id} с body {"status": "interview"}. Авторизация: сервис проверяет что application.user_id == ctx_user_id (иначе 403). applied_at заполняется при переходе в статус "applied".
